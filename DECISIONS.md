# DECISIONS — журнал решений pro_contakt

> **Статус:** Утверждено. Ведётся по каждому значимому решению.
> **Назначение:** зафиксировать, что решено, почему именно так и какие последствия — чтобы не восстанавливать причины по истории чатов.
> **Дата последнего содержательного пересмотра:** 2026-09-24.

Гранулярность: одна запись на каждый решённый пункт или задачу, а не на pull request — несколько решений могут войти в один PR.

---

### DEC-001. Право утверждения требований и merge
**Дата:** 2026-09-24
**Решение:** утверждать требования, принимать результат работы и выполнять merge в `main` может только владелец проекта.
**Причина:** проект пока ведёт один ответственный человек; ИИ-ассистенты не обладают полномочиями принимать необратимые решения самостоятельно.
**Последствия:** ИИ готовит черновики и предложения, но PR и merge всегда выполняет владелец вручную.
**Источник:** архивный черновик, §22 п.1.

### DEC-002. Автономия ИИ и согласование коммитов — без дублирования в проектных правилах
**Дата:** 2026-09-24
**Решение:** вопрос, какие действия ИИ может выполнять самостоятельно и когда нужно отдельное согласование коммита/публикации ветки, регулируется личными инструкциями пользователя для конкретного ИИ-инструмента, а не проектным регламентом.
**Причина:** личное правило пользователя (модель «Анализ → Обсуждение → Выполнение») уже обязательно для всех используемых им ИИ и имеет приоритет; дублирование создало бы риск рассинхронизации двух источников истины.
**Последствия:** `AGENTS.md` и архивный черновик ссылаются на внешнее правило, а не переписывают его.
**Источник:** архивный черновик, §22 п.2–3; `AGENTS.md`, §2.3.

### DEC-003. Стратегия ветвления
**Дата:** 2026-09-24
**Решение:** `main` — основная ветка; короткие тематические ветки создаются от неё (`planning/...`, `feat/...`, `fix/...`, `docs/...`); отдельных `develop`/`release` веток нет.
**Причина:** масштаб проекта пока не требует многоступенчатой модели ветвления; простая модель снижает накладные расходы.
**Последствия:** каждая задача — отдельная ветка от актуальной `main`, PR напрямую в `main`.
**Источник:** архивный черновик, §22 п.4.

### DEC-004. Набор документов для первой версии сайта
**Дата:** 2026-09-24
**Решение:** для v1 нужен расширенный набор документов сразу: канонический регламент (`AGENTS.md`), требования к v1, `WORK_PLAN`, глоссарий, `DECISIONS`, `README`, `ROADMAP`, `CHANGELOG`. Документы, специфичные для CRM, создаются только при начале работы над CRM.
**Причина:** проект должен быть понятен новому участнику без доступа к истории чатов; создание набора сразу дешевле, чем дорабатывать его позже по частям.
**Последствия:** документы создаются последовательными отдельными задачами (`AGENTS.md` и архивирование черновика — сделано; `ROADMAP`/`WORK_PLAN`/`CHANGELOG`/`DECISIONS` — эта задача; требования к v1, глоссарий, `README` — далее).
**Источник:** архивный черновик, §22 п.5.

### DEC-005. Языки сайта
**Дата:** 2026-09-24
**Решение:** публичный сайт — на русском и английском языках; внутренняя документация — на русском.
**Причина:** соответствует целевой аудитории и юрисдикции (см. DEC-006); английская версия расширяет охват.
**Последствия:** контент сайта закладывается сразу двуязычным; локализация — часть требований к v1.
**Источник:** архивный черновик, §22 п.6; §9.3, §10.1.

### DEC-006. Юрисдикция
**Дата:** 2026-09-24
**Решение:** фирма работает в юрисдикции Россия / СНГ.
**Причина:** определяет применимое законодательство о персональных данных и правовые тексты сайта.
**Последствия:** формы заявки, обработка персональных данных и правовые тексты ориентируются на законодательство РФ/СНГ.
**Источник:** архивный черновик, §22 п.7.

### DEC-007. Основные каналы учёта заявок
**Дата:** 2026-09-24
**Решение:** два связанных основных канала учёта заявок — форма на сайте и Telegram. Данные из формы автоматически дублируются в Telegram и на email; сообщения, написанные напрямую в Telegram, попадают только в Telegram. Остальные каналы (Instagram, ВКонтакте, WhatsApp, телефон) публикуются на сайте как способы связи, но не входят в основной контур учёта.
**Причина:** нужен единый предсказуемый контур учёта заявок, чтобы обращения не терялись между множеством каналов (требование архивного черновика §15.17), при этом фирма хочет присутствовать во всех перечисленных каналах связи.
**Последствия:** техническая реализация формы обязана дублировать заявки в Telegram и email; остальные каналы — витрина контактов без гарантии единого учёта на первом этапе.
**Источник:** архивный черновик, §22 п.8, §15.17.

### DEC-008. Обязательные проверки перед слиянием и выпуском
**Дата:** 2026-09-24
**Решение:** полный набор обязательных проверок — сборка, линтинг, проверка типов, тесты, доступность, базовая проверка безопасности.
**Причина:** сайт — точка первого контакта с клиентом; экономия на проверках создаёт риск потери заявок и репутации.
**Последствия:** PR не мержится без прохождения полного набора; невыполненная проверка помечается «Не проверено», а не считается пройденной.
**Источник:** архивный черновик, §22 п.9.

### DEC-009. Роли и данные CRM — решение отложено
**Дата:** 2026-09-24
**Решение:** обсуждение ролей и прав доступа будущей CRM переносится на момент начала работы над CRM.
**Причина:** CRM — направление развития, а не утверждённая часть первой версии сайта; преждевременное проектирование ролей рискует не совпасть с реальными требованиями, когда до CRM дойдёт очередь.
**Последствия:** пункт остаётся открытым в архивном черновике (§22 п.10) и в `ROADMAP.md` до старта соответствующей задачи.
**Источник:** архивный черновик, §22 п.10.

### DEC-010. Отдельное создание ветки `main` и назначение её веткой по умолчанию
**Дата:** 2026-09-24
**Решение:** создать ветку `main` от начального коммита `a673bcb`, запушить на GitHub и вручную назначить её веткой по умолчанию в настройках репозитория.
**Причина:** репозиторий изначально создавался сразу в `planning/site`, ветки `main` на GitHub не существовало; без неё pull request и сравнение веток не работали.
**Последствия:** ветвление теперь соответствует принятой модели (DEC-003); дальнейшие ветки создаются от актуальной `main`.
**Источник:** обсуждение сессии 2026-09-24 (диагностика через `git ls-remote`).

### DEC-011. Обязательное ядро правил вынесено в канонический `AGENTS.md`
**Дата:** 2026-09-24
**Решение:** создать `AGENTS.md` в корне репозитория как единственный обязательный свод правил; архивный черновик остаётся источником рекомендаций и чек-листов, не входящих в обязательное ядро.
**Причина:** черновик из ~300 строк слишком велик и не разделяет обязательное и рекомендательное; новому участнику (человеку или ИИ) нужен короткий однозначный вход.
**Последствия:** при противоречии между `AGENTS.md` и любым другим документом репозитория приоритет у `AGENTS.md`; архивный черновик помечен как заменённый со ссылкой.
**Источник:** архивный черновик, §22 п.11 (закрыт этим решением); §21 (предложенный механизм).

### DEC-012. Гранулярность записей CHANGELOG
**Дата:** 2026-09-24
**Решение:** в `CHANGELOG.md` одна запись соответствует одному решённому пункту или выполненной задаче, а не одному pull request — даже если несколько решений вошли в один PR.
**Причина:** запись по PR слишком крупная, чтобы быть полезной при поиске причины конкретного решения; более мелкая гранулярность прослеживается до записи в `DECISIONS.md`.
**Последствия:** `CHANGELOG.md` может содержать несколько записей с одинаковой ссылкой на PR.
**Источник:** обсуждение сессии 2026-09-24.
